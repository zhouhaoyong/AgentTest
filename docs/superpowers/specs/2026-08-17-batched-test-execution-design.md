# 批量测试执行与显式启动设计

## 目标

降低多个测试点之间重复打开页面、重复定位、重复写文件和重复推理造成的执行成本，并避免 Agent 在页面等待或弹窗异常时长时间无反馈地卡住。

## 方案

采用“批量编写、分组调试、按测试点执行”的混合流程：

1. 测试点批准后，先一次性生成当前范围的脚本骨架，并抽取登录、导航、弹窗、列表切换等公共步骤。
2. 在正式业务操作前，按页面 / 业务流程分组做定位器、页面到达和前置数据探针；探针不扩大测试范围，也不执行高影响写操作。
3. 正式执行时，一个测试组复用同一个隔离浏览器会话，但仍以单个测试点作为结果、报告和断点续跑的最小单位。
4. 测试点之间不重新启动浏览器、不重新规划整轮流程；每完成一个测试点才写一次状态、报告和进度。
5. 每个操作有超时和有限重试；单个测试点或一段时间没有可观察进展时自动停下，记录 `BLOCKED` / `NOT RUN` 并报告当前步骤，不无限等待。
6. 测试点确认和正式测试启动分离：测试点确认只表示范围获批，只有用户明确说“开始正式测试”或等价表达后才打开浏览器。

## 边界

- 失败的独立测试点可继续执行；依赖同一前置数据或同一页面状态的测试组应先暂停。
- 不把测试状态、执行结果和证据更新视为测试范围变更；修改步骤、预期结果或覆盖范围仍需重新确认。
- Element Map、Memory 和需求只沉淀已验证且具有长期复用价值的事实。

## 成功标准

- 测试点确认后 Agent 不会自行启动浏览器。
- 多个测试点可以先形成可复用脚本，再进入正式执行。
- 用户可以持续看到当前测试点、当前子步骤、等待原因和下一次熔断时间。
- 单个测试点出现异常时不会无限重试，也不会拖住整个测试批次。
