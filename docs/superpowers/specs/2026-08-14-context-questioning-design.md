# 上下文提问分层设计

## 目标

让 AgentTest 在新项目首次对话时只收集启动测试所必需的业务上下文，不把内部 ID、测试账号、角色或业务测试数据当成用户必须立即提供的信息。

## 交互契约

首轮上下文确认只询问：

- Project 中文名称；
- 要测试的 System 名称、系统类型和必要的模块范围；
- Version 版本号或版本名称；
- 测试地址，并确认不是未经允许的生产环境；
- 原始需求或需求来源；
- 只有确实存在多个 System 联动时，才询问参与系统和操作顺序。

用户只需提供业务可读名称。Agent 根据名称生成目录安全 ID，并展示 `name → id` 映射供用户确认；ID 不作为英文名提问，也不作为被测系统业务数据提问。若生成的 ID 冲突、含义不清或用户不接受，才要求用户调整。

## 权限与测试数据分层

角色、权限、账号可用性和业务测试数据不是通用的上下文问题。需求整理后，Agent 先判断当前需求是否涉及登录、角色差异、数据范围、数据隔离或多账号流程：

- 不涉及：不询问账号、角色或测试数据；
- 涉及角色/权限：询问需要覆盖的角色和是否有可用测试账号，但不索要密码、Token、Cookie 或 Storage State；
- 涉及具体业务数据：只询问测试点所需的数据条件和已有数据是否可用，不自行编造订单、用户或资料组合。

正式测试需要登录时，继续由用户手动登录；不同角色使用独立会话。凭据不得写入资产、日志、截图、脚本或报告。

## 阶段边界

`workflow/context/prompt.md` 负责最小上下文和 ID 映射确认；`workflow/requirements/prompt.md` 负责需求澄清及按需判断角色、权限和测试数据前置条件；`workflow/testing/rules.md` 继续负责手动登录和凭据安全。不得在上下文阶段预设具体业务数据或角色覆盖范围。

## 验收标准

- 公共入口示例使用“项目名称、系统、版本、地址、需求来源”等业务语言；
- 上下文 Prompt 明确 ID 由 Agent 建议生成，不要求用户提供英文名；
- 上下文 Prompt 明确账号、角色和测试数据按需求后置确认；
- 需求 Prompt 明确只有相关需求才询问角色、权限和数据前置条件；
- 正式测试规则继续禁止索要或保存凭据；
- 静态测试能防止首轮 Prompt 回退为“必填账号/角色/英文 ID”。

## 非目标

- 不修改 Project / System / Version Schema；
- 不新增 ID 自动生成运行时或命令行工具；
- 不改变测试点审批、浏览器测试或报告格式；
- 不执行 Git 操作。
