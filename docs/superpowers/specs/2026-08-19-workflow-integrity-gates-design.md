# 测试完整性闸门设计

> 来源：用户确认的九项工作流问题及“方案 2：统一测试完整性闸门”。
> 范围：公共脚手架、校验能力、模板、说明材料和自动化回归；不修改 projects/ 中的业务资产。

## 1. 目标

让一次测试从用户提出要求到交付报告，始终能够回答四个问题：

1. 用户明确要求的内容是否被逐条承接并完成。
2. 测试用例、执行进度和报告是否对同一结果给出同一说法。
3. 测试是否只在已确认、可用且正确的环境和联动范围内执行。
4. 报告中的结论是否有对应的脚本、执行记录和证据可追溯。

目标不是把 AgentTest 改造成调度平台，而是让文件化工作流中的关键事实可校验、可阻断、可回归。

## 2. 范围与边界

- Markdown 和 YAML 仍是唯一事实来源。
- 不新增独立服务、数据库、凭据保存、浏览器扩展、固定命令行入口或远程调用。
- 不写入或修改真实业务 Project；测试使用的账号、Cookie、Token、业务样本和临时会话均不进入资产。
- 闸门由工作流 Agent 在指定阶段调用。没有独立调度服务时，无法阻止恶意或完全不遵守规则的外部 Agent；但合规工作流将无法在资产校验中通过缺少闸门所要求事实的交付物。

## 3. 总体流程

    用户明确要求
      → 关键覆盖约束
      → 测试用例与批准范围
      → 开测前完整性闸门
      → 脚本与实际执行结果
      → 交付前完整性闸门
      → 报告结论

每个箭头只允许向后传递已经校验过的事实。发现范围、环境、结果或证据不一致时，停在当前阶段说明原因，不自动替用户补充业务假设。

## 4. 关键覆盖约束

### 4.1 资产格式

测试用例文档的“关键覆盖约束”使用稳定编号，例如 KC-001。每条至少包含：

- 用户要求：用户原话的业务含义。
- 承接用例：一个或多个当前测试用例 ID。
- 完成标准：何种执行覆盖和结果才算满足。
- 当前状态：未开始、已满足、部分阻塞或未满足。

同一条约束可由多个用例共同承接；一个用例也可承接多条约束。不得把“关键覆盖约束”只留在聊天记录、需求说明或报告散文中。

### 4.2 批准保护

批准范围指纹纳入关键覆盖约束的完整内容及其用例映射。确认后删改约束、承接用例或完成标准，都会触发重新确认；执行字段和当前状态不进入指纹，以便正常记录执行过程。

### 4.3 交付判定

交付前逐条计算约束状态：

- 所有承接用例完整执行，且满足完成标准：已满足。
- 任一承接用例失败：未满足。
- 任一承接用例阻塞、未运行、未执行，或无法判断：部分阻塞。

存在未满足或部分阻塞的关键覆盖约束时，报告不得宣称通过。

## 5. 统一结果口径

### 5.1 单一对应关系

每个测试用例在以下位置必须使用同一结果：

- 测试用例中的执行覆盖和测试结果。
- state.yaml 中该用例的内部结果。
- 报告明细中的执行覆盖和本次结果。

内部结果与展示结果的对应关系固定为：

| 内部结果 | 报告/用例结果 | 允许的执行覆盖 |
| --- | --- | --- |
| passed | PASS | 完整 |
| failed | FAIL | 完整 |
| blocked | BLOCKED | 部分或未执行 |
| not_run | NOT RUN | 未执行 |

state.yaml 只记录执行进度和机器读取值，不能单独成为对用户的最终结论。

### 5.2 报告结论

报告顶部继续保留第一屏结论和数字，但其总数、是否可宣称通过和关键约束状态必须与明细一致。出现 FAIL、BLOCKED、NOT RUN、未满足关键约束、零个有效执行用例中的任一种，均不可宣称通过。

## 6. 三道完整性闸门

### 6.1 测试用例确认闸门

在要求用户确认测试用例前校验：

- 每条关键覆盖约束均有稳定编号、承接用例和完成标准。
- 引用的测试用例均真实存在，且关键覆盖要求没有遗漏。
- 当前测试用例范围可生成批准指纹。
- 单系统或联动系统的上下文、版本和测试地址事实完整。

通过后才可记录批准指纹；失败时只说明缺少的业务事实或资产，不进入正式测试。

### 6.2 正式测试启动闸门

在打开浏览器前校验：

- 当前测试用例范围与批准指纹一致。
- 当前 Version 明确填写测试地址，并已确认不是未经允许的生产环境。
- 参与联动的每个对端 System、Version 和测试地址均真实存在且已明确。
- 上次中断后的已完成用例、结果和当前测试用例记录一致。

任何联动对端未写明 Version 时，必须在此处解析并写成明确 Version 后重新确认；不得猜测“当前范围”。

### 6.3 报告交付闸门

在交付报告前校验：

- 用例、state.yaml 和报告对每个用例的结果和执行覆盖一致。
- 已执行用例存在可追溯脚本；报告中引用的脚本真实存在并声明对应测试用例。
- 报告统计、顶部结论和关键覆盖约束状态一致。
- Bug、阻塞和数据缺口均关联相应测试用例；数据缺口不被直接表述为业务缺陷。
- 有证据目录时，其目录契约和报告引用完整；证据不包含凭据。

## 7. 环境和联动事实

### 7.1 测试地址

当前 Version 的 test_url 是唯一可执行测试地址。System 的 base_url 保留为说明性历史字段或兼容字段，不参与地址回退。test_url 为空时，正式测试启动闸门必须失败并要求用户确认本次测试地址。

### 7.2 多系统联动

联动关系在各自 Version 的 version.yaml 中维护，但资产校验从 Project 范围解析每个引用：

- System 目录存在。
- Version 目录和 version.yaml 存在。
- 对端 Version 的 test_url 非空。
- 引用不重复、不指向自身，且操作顺序可确定。

Schema 继续校验单个文件的格式；跨目录真实性由项目级校验负责。

## 8. 脚本、探索和说明材料

### 8.1 测试脚本追溯

脚本按模块或业务流程组织，可覆盖多个用例，但文件头必须列出覆盖的测试用例 ID、前置条件、手动登录安排、运行方式、数据缺口处理和结果判断。资产校验将比对脚本声明、测试用例范围和报告引用，不再只检查是否出现一段说明文字。

### 8.2 探索止损接线

探索阶段把预算、批量候选验证和定位评分作为标准操作：每次目标入口尝试、无进展和候选定位验证都使用已有探索工具记录和判断。预算触发时结束本轮探索、沉淀已有事实并向用户说明阻塞原因。仍不新增 CLI；工具以库形式被工作流调用。

### 8.3 Demo 同步

Demo 展示当前模板中的关键覆盖约束、证据目录、脚本追溯和报告结论。模板章节、必填字段或闸门规则变化时，自动化测试同步验证 Demo 的关键概念和章节引用，避免“首次阅读材料”引导旧做法。

## 9. 校验能力的组织方式

扩展现有资产校验，而非新建第二套事实来源：

- Version 级校验：测试用例、关键覆盖约束、state.yaml、脚本、证据、报告和批准指纹。
- System 级校验：现有 Element Map 与 Memory。
- Project 级校验：Project/System/Version YAML 合法性、当前上下文、联动端解析和测试地址。
- 阶段闸门：复用上述校验，按确认、开测、交付选择适当的检查集合并产出业务可读的阻塞说明。

校验函数保持纯读取和结构化结果，不自行创建、改写或删除业务资产。

## 10. 回归策略

新增一个临时目录中的“标准流程样本”，不访问真实系统。它覆盖：

1. 关键覆盖约束改动会改变批准范围。
2. 关键覆盖约束引用不存在用例时被拦截。
3. state.yaml、测试用例和报告结果冲突时被拦截。
4. 结果汇总或“可宣称通过”与明细不一致时被拦截。
5. 测试地址为空、联动对端不存在或对端地址为空时被拦截。
6. 脚本声明与测试用例或报告引用不一致时被拦截。
7. Demo 与模板的关键规则或章节引用不一致时被拦截。
8. 探索预算和批量发现流程确实在工作流调用点被使用。

保留现有单元测试；每批改动后运行 Ruff 和完整 Pytest。最终回归不需要真实登录或浏览器业务数据。

## 11. 验收标准

- 用户的最低覆盖要求无法在确认后静默丢失。
- 任一用例在三份执行记录中的结果无法相互矛盾。
- 不满足地址、联动或批准范围条件时无法进入正式测试。
- 不满足脚本、证据、汇总或关键约束条件时无法通过报告交付校验。
- Demo、模板和规则对同一流程给出一致指导。
- 探索止损工具有真实工作流调用点。
- 全量自动化测试和静态检查通过。
