# 正式测试阶段规则

本文件仅补充正式测试阶段行为；目录、凭据、手动登录和 Git 的全局规则以 `AGENTS.md` 为准。

## 开跑前校验（pre-flight）

- 正式点击前先确认：测试地址可达、非未经允许的生产环境、测试用例依赖的前置数据存在、需要的账号 / 角色就绪。任一不满足先停下向用户确认。
- 除“可达”外做一次轻量“目标页可读性探针”：能否稳定读取目标页的关键区域 / 导航。读不动（持续超时）就当场停下向用户说明并反问，不要先宣布开跑、再把测试用例整批标 `BLOCKED`。

## 批准指纹与断点续跑

- 用户批准时对最终 `test-cases/test-cases.md` 的测试范围生成指纹并记入 `.agentest/state.yaml` 的 `test_cases_fingerprint`。指纹覆盖范围内容，不覆盖`测试状态`、`执行覆盖`、`测试结果`、`实际结果`、`执行时间`和`证据`等执行字段。
- 每次开跑（含续跑）前重新比对范围指纹，指纹变化说明批准后的测试范围被改动，必须停下重新取得确认再更新指纹。
- 每完成一个测试用例就即时更新该测试用例的执行字段、写入 `report/report.md`，并把测试用例 ID 追加到 `completed_test_case_ids`；中断后重新进入时跳过已完成项、从下一个未完成测试用例继续。执行字段和 `completed_test_case_ids` 只记录结果 / 进度，不作为长期授权，续跑仍需过范围指纹校验。

## 范围与结果

- 用户明确说“开始正式测试”后，重新读取当前 Version 的完整 `test-cases/test-cases.md`，仅执行其中的最终内容；测试用例确认不等于正式测试，测试用例确认不等于正式测试启动。
- 测试开始后先批量生成当前范围脚本，再按页面 / 业务流程分组调试定位器和前置数据；正式结束前至少实际运行一次脚本并记录运行方式；不得一个测试用例从编写、调试到执行完毕后才开始下一个。
- 正式执行时按测试用例记录结果，同组测试用例复用同一个隔离浏览器会话；每完成一个测试用例才更新状态、报告和进度，不在每个点击动作后重新规划和写文件。
- 每个 Test Case 记录 `执行覆盖`（完整/部分/未执行）和 `PASS`、`FAIL`、`BLOCKED` 或 `NOT RUN`；只有完整执行才能 PASS/FAIL，部分执行必须 BLOCKED，环境异常不直接判定为业务 Bug。
- 发现范围外问题可记录，但不得自行补测或改变当前测试用例。测试结束后，只把已验证且具有长期复用价值的事实同步到需求、Element Map、Memory、测试用例或报告；不把推测、临时现象或错误信息沉淀为最终资产。
- 执行中发现需求解释变化时必须暂停确认；若改变步骤、预期、前置条件或测试范围，重新确认并更新批准指纹。

## 浏览器与数据

- 所有正式测试统一使用内置隔离浏览器（由 Playwright 驱动系统 Google Chrome 的无痕 / 隔离会话），不再区分"优先 / 其次"两级后端。禁止使用 Edge、Playwright bundled Chromium。禁止复用用户当前已打开的浏览器窗口、Tab、Profile 或地址；必须使用新建的隔离 Chrome 会话。无法确认隔离或没有可用 Chrome 能力时先停止，并询问用户是否需要 Agent 协助安装或启用，未确认前不得打开浏览器。使用 `BrowserSession`（Playwright）时必须是全新 headed 隔离会话，不加载用户的 Chrome 配置、缓存和登录态。
- 视口按系统类型：web 使用真实最大化窗口（`--start-maximized` + `no_viewport`，绝对尺寸随机器变，需在 Element Map 记录验证视口）；H5 / app / miniapp 使用移动端视口（如 iPhone 14 Pro 393×852、DSF 3、触屏）。
- 复用同一本地隔离会话，不每步重连或重启，减少每步往返开销；底层连接方式不影响用户确认的测试范围，也不要求用户提供或理解相关配置。
- 重页面（大列表 / 多卡片）避免整页 DOM / 可访问性树快照——快照过大既慢又烧 token；改为只读当前要操作的小容器，或用截图 / 视觉确认布局。
- 点击后确认当前页变化、新页面、外部页面或下载，再继续操作。外部页面只验证跳转；下载核对文件名、格式和必要内容。
- 多个 System 时按测试用例顺序操作，并在下一系统核对结果。数据更新时等待可观察结果和测试用例写明的最长时间，不固定时间盲等。
- 统计、指标或汇总需求在相同口径、时间范围和筛选条件下与参考数据比较；没有参考数据时记录阻塞。
- 成功提示不等于通过；需要在目标页面、数据或后续步骤中确认最终结果。
- 使用稳定定位；高影响操作前确认目标和环境，只处理明确测试数据。
- 测试结束或异常退出时先保存证据和状态，再自动关闭页面、Context、Browser 和 Playwright；不询问用户是否关闭。
- 单个操作最多重试 1 次；单个测试用例运行超过 5 分钟，或连续 60 秒没有可观察进展，自动暂停并报告当前测试用例、当前子步骤和等待原因，记录为 `BLOCKED` / `NOT RUN`，不得无限等待。

## 弹窗与等待

- 弹窗超时多数是等待时间偏短加未等动画 / 遮罩所致，并非 Playwright 不稳，也基本不是 iframe（Vue3 + UI 框架的弹窗通常通过 teleport 挂在 `body` 下的普通 DOM，而非 iframe）。
- 默认操作超时为 10 秒，可按 System 在环境配置中覆盖；不要靠固定 sleep 盲等。
- 操作弹窗前，先等它可见且过渡动画结束（元素稳定、可交互），用 `role=dialog` 等限定作用域再定位内部元素。
- 关闭弹窗后，等待弹窗与遮罩层（如 `.el-overlay`、`.ant-modal-mask`）真正消失再继续，避免残留遮罩拦截后续点击。
- 避免使用 `networkidle` 作为等待条件（页面有轮询 / websocket 时永不 idle）；等待具体的可观察元素或状态。

## 页面到达与读取超时

- 分离“到达”与“读取”：导航到目标页不以整页 DOM 读取为前提；只读当前要操作的小容器或用截图确认布局，不做整页 DOM / 可访问性树快照。
- 到达方式按成本择优并现场校验落点：深链直达 → 稳定导航文案点击 → 站内搜索 / 快捷入口；深链被重定向回登录 / 首页时自动退到下一种。
- 构造 URL 要谨慎：hash 路由（`#/...`）的 query 参数必须放在 `#` 之前（如 `/path/?debug=1#/page`）；不凭空手拼，以标签页当前真实 URL 为基准改写；改动 URL 后需整页重载，并读回标签页实际 URL 确认已真正切换，避免旧标签页状态造成“看似没生效”。
- 连续超时按降级链处理：锚点等待 → 局部读取 → 单步操作 → 仍不行则判 `BLOCKED`，记录“读取 / 到达受阻”，保留已确认的稳定事实（如落地路由、导航文案），不编造未验证的路径、按钮或定位。
- 若页面在自动化（CDP）接入后整体冻结或出现 `js execution timed out`，先排查被测系统是否有反调试 / devtools 检测机制；一旦怀疑，停下向用户说明并反问如何继续，不擅自绕过。任何项目专属的绕过办法或放行开关都不写进脚手架，也不落进 `projects/` 资产。

## 证据与脚本

- Bug 证据（截图、Trace、HAR、录像等）统一保存在当前 Version 的 `evidence/` 目录，并在报告的对应 Bug 中引用相对路径。
- 证据保留足以判断问题的原始状态，但不得包含敏感凭据；截图 / Trace / HAR 中若含 Token、Cookie、密码等需先脱敏或不入库。
- 仅将稳定、可重复且当前范围可复用的逻辑保存为 Test Script；临时探索或调试代码不入库。
