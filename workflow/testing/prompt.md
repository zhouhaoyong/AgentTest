# 正式测试 Prompt

你正在执行当前 Version 或联动范围已获用户明确授权的正式测试。

## 进入条件

- 用户明确表示“开始正式测试”或等价表达；测试点确认不等于正式测试，测试点确认不等于正式测试启动，只表示范围获批，不自动启动测试。
- 当前 Project、相关 System、Version 或联动范围、测试地址与环境可用，且不是未经确认的生产环境。

## 开跑前校验（pre-flight）

正式点击第一个测试点之前，先完成下面的快速校验，任一项不满足就停下向用户确认，不要贸然开跑：

1. **地址可达**：测试地址能正常打开、非空白 / 非报错页。
2. **非生产环境**：确认地址不是未经允许的生产环境（数据安全、写操作风险）。
3. **数据就绪**：测试点依赖的前置数据存在（如待审批单据、目标记录）；缺失则记为 `BLOCKED` 或先补数据。
4. **账号就绪**：需要登录 / 特定角色时，账号可用；需要手动登录时按停止条件暂停等用户完成。
5. **可读性探针**：除“可达”外，快速确认目标页关键区域 / 导航能否稳定读取；读不动（持续超时）就停下向用户说明并反问，不先宣布开跑再整批标记 `BLOCKED`。

## 批准指纹校验（防漂移）

- 用户批准测试点时，对最终 `test-points/test-points.md` 的测试范围生成指纹（如内容哈希）并记入 `.agentest/state.yaml` 的 `test_points_fingerprint`。
- 指纹只覆盖测试点标题、前置条件、步骤、预期结果、关联需求和测试维度等范围内容；`测试状态`、`测试结果`、`实际说明`、`执行时间`、`证据`属于执行记录，不纳入指纹。
- 每次开跑前重新计算当前测试点范围指纹并与记录比对：一致才直接执行；不一致说明批准后的测试范围被改动，必须停下、向用户说明差异并重新取得确认，再更新指纹后执行。
- 从不把"已批准"作为可长期复用的状态回写；续跑或再次进入测试都要经过上述指纹比对，避免静默自动跑。

## 必读资料

1. 根目录 `AGENTS.md`、当前 Version 或联动范围的配置、`requirements/` 和 `test-points/requirement.md`。
2. 当前范围最终的完整 `test-points/test-points.md`；它是本次唯一测试范围。
3. 相关 System 的 `system.yaml`、Test Scripts、Memory、Element Map 和环境配置。
4. [`rules.md`](rules.md)。

## 决策与执行

每次执行前，先用一句话说明“做什么”，再用一句话说明“为什么”；例如先检查测试点、地址、数据和浏览器能力，是为了避免在范围或会话不安全时误操作。

1. 重新读取当前测试点文件；仅执行其中内容，不依据旧会话、旧状态或过去的测试点版本推断范围。
2. **批量生成与分组调试**：先一次性生成当前批准范围的脚本骨架，抽取登录、导航、弹窗、列表切换等公共步骤；再按页面 / 业务流程分组调试稳定定位器和前置数据。探针只验证到达、读取、定位和数据就绪，不执行未经批准的高影响业务写操作。
3. **增量结果与断点续跑**：正式执行时同组测试点复用同一个隔离浏览器会话；每完成一个测试点才更新该测试点的`测试状态`、`测试结果`、`实际说明`、`执行时间`和`证据`，同时把结果写入 `report/report.md`，并把该测试点 ID 追加到 `.agentest/state.yaml` 的 `completed_test_point_ids`。不得在每个点击动作后重新规划和写文件。若本轮被中断后重新进入，先读取 `completed_test_point_ids`，跳过已完成项、从下一个未完成测试点继续，避免整轮重跑或漏跑；续跑同样要先过上面的批准指纹校验。
4. 运行浏览器 pre-flight 检查。所有正式测试使用 Google Chrome；内置隔离浏览器只有在确认使用 Chrome 时才优先，否则使用能创建新 Chrome 无痕 / 隔离会话的 Playwright 能力。禁止使用 Edge、Playwright bundled Chromium。禁止复用用户当前已打开的浏览器窗口、Tab、Profile 或地址；必须使用新建的隔离 Chrome 会话。如果没有可用 Chrome 能力，先询问用户是否需要 Agent 协助安装或启用，未确认前不得打开浏览器。点击后确认是当前页变化、新页面、外部页面还是下载；切到正确位置后再继续。
4. 每个 Test Point 记录 `PASS`、`FAIL`、`BLOCKED` 或 `NOT RUN`。环境、登录或网络异常应记录为 `BLOCKED` / `NOT RUN`，不能直接判定为业务 Bug。
5. Bug 必须关联测试点，记录前置条件、复现步骤、实际结果、预期结果、影响和必要且不含凭据的证据；证据文件统一放在当前 Version 或联动范围的 `evidence/` 目录。
6. 多个 System 时按测试点顺序操作，并在下一系统核对结果。数据有延迟时等待写明的结果和最长时间，不固定等待几秒；成功提示不等于通过，最终要在目标页面或数据中核对。
7. 统计、指标或汇总需求按测试点写明的口径、时间范围和筛选条件，与参考数据比较；没有参考数据时记录 `BLOCKED`，不把页面数字直接判为准确。
8. 只在批准范围内使用可识别测试数据；删除、批量修改、提交或审批等高影响操作须确认目标和环境。
9. **等待熔断**：单个操作最多重试 1 次；单个测试点运行超过 5 分钟，或连续 60 秒没有可观察进展，自动暂停并报告当前测试点、当前子步骤和等待原因，记录为 `BLOCKED` / `NOT RUN`，不得无限等待。

## 允许写入的位置

- 当前 Version 或联动范围的 `test-scripts/`、`report/report.md`、Bug 证据目录 `evidence/`，及当前结构化需求中的测试后实现说明。
- 当前 Version 或联动范围的 `test-points/test-points.md` 中每个测试点的执行字段：`测试状态`、`测试结果`、`实际说明`、`执行时间`和`证据`。
- `.agentest/state.yaml` 的进度字段：`completed_test_point_ids`（增量进度）和 `test_points_fingerprint`（批准范围指纹）。
- 仅当信息长期可复用且已验证时，更新对应 System 的 Memory 或 Element Map；测试结束后同步核对结构化需求、测试点和报告，只沉淀已确认的事实。
- 不回写测试点授权状态（执行字段和 `completed_test_point_ids` 只记录结果 / 进度，不等于授权），不保存凭据、临时会话或一次性调试脚本；`evidence/` 中的证据不得包含任何凭据。

## 交付物与移交方向

- 测试结束后更新可重复执行脚本和唯一报告，并向用户汇报结果分布、Bug、未测内容、阻塞项、风险和建议。
- 报告整理需求单独移交 `reporting/`；Bug 修复后的回归需求移交 `regression/`。

## 强制停止条件

- 遇到登录立即暂停，由用户手动完成并明确确认。
- 测试完成后不得扩大范围或继续执行新的测试任务，除非用户明确要求。
