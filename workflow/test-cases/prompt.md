# 测试用例设计 Prompt

你正在基于当前 Version 的最终需求设计可执行、可评审的测试用例。每个测试用例描述一个独立、可执行、可判断结果的验证场景。

## 进入条件

- 当前 Version 的结构化需求已完成。
- 已完成探索决策；需要探索的部分已完成，或已确认复用已有知识。
- 用户尚未授权开始正式测试。

## 必读资料

1. 根目录 `AGENTS.md` 与当前 Version 的配置、`requirement.md`、`requirements/`。
2. 当前范围已有的 `test-cases/`（如存在）。
3. 相关 System 的 `system.yaml`、Memory 与 Element Map 模块。
4. [`template-test-cases.md`](template-test-cases.md)，它是测试用例文档的唯一完整模板。

## 决策与执行

1. 先分析功能模块、业务对象和状态、主流程与分支、输入校验与边界、角色权限、页面衔接以及未知项。多个 System 时写清涉及的系统、操作顺序和最终结果在哪里核对。
2. 把用户在对话中明确提出的最低覆盖、必须验证、明确排除和数据前置要求整理到“关键覆盖约束”中；每条约束使用 KC-001 等稳定编号，写清用户要求、承接它的 Test Case、完成标准和当前状态。关键约束不能只留在聊天记录或结构化需求中。
3. 每个 Test Case 使用稳定 ID、名称、关联需求、优先级、测试维度、必要的前置条件/测试数据、步骤、可判断的预期结果、测试状态、执行覆盖和测试结果。新建测试用例默认“测试状态：未测试、执行覆盖：未执行、测试结果：NOT RUN”；实际执行并完成所有步骤和子场景后改为“测试状态：已测试、执行覆盖：完整”。只完成部分步骤或缺少必要业务数据时使用“执行覆盖：部分、测试结果：BLOCKED”；没有开始执行时使用“执行覆盖：未执行、测试结果：BLOCKED/NOT RUN”。保持状态组合一致：`未测试 + 未执行 + BLOCKED/NOT RUN`、`部分 + BLOCKED`、`已测试 + 完整 + PASS/FAIL` 分别表示尚未开始、已开始但未完成、已完成并得出结论。
4. 按实际需求覆盖功能、业务流程、角色/权限场景；不强行生成无意义分类或字段。P0 表示核心流程、关键数据或严重权限风险，P1 为重要功能和常见异常，P2 为低频或影响较小场景。
5. 统计、指标或汇总需求写清口径、时间范围、筛选条件和参考数据；多个 System 或数据更新有等待过程时，写清等待什么结果和最长等待时间。
6. 在测试范围中记录探索策略（复用已有知识、目标探索或必须探索）、依据、已覆盖、未覆盖/阻塞、开放问题和风险。
7. 需求、Memory 与 Element Map 冲突，或关键未知项会影响测试范围或预期结果时，先向用户提问；不把推断写成测试用例。
8. 页面或元素是否已核验不再作为测试用例名称标记；页面读取或定位问题在正式测试中按实际结果记录为 `BLOCKED` 或 `NOT RUN`，不新增“页面审核”状态。
9. 一个测试用例包含多个独立入口、状态或角色时，优先拆成子测试用例；无法拆分时必须在执行覆盖和实际结果中逐项列出已执行与未执行场景，不得用整体 `PASS` 隐藏未覆盖分支。
10. 向用户请求测试用例确认前，执行测试用例确认闸门；若关键约束没有承接用例、完成标准不完整、地址未确认或范围校验失败，先补齐事实或向用户说明阻塞，不请求确认。

## 允许写入的位置

- 只更新当前 Version 的 `test-cases/test-cases.md`，使用相邻唯一模板作为结构参考。
- 不修改无关资产，不在 `workflow/` 写真实测试用例，不启动浏览器、不修改业务数据。

## 交付物与移交方向

- 向用户汇报测试用例路径、数量与 P0/P1/P2 分布、覆盖范围、未覆盖/阻塞项、开放问题和风险。
- 用户明确说“开始正式测试”或等价表达后，才移交 `testing/`；执行前由测试阶段重新读取当前文件的完整内容。

## 强制停止条件

- 写完或更新 `test-cases/test-cases.md` 后立即停止。
- 不写 `Draft`、`Approved` 等批准状态，不执行测试，不调用正式测试流程；“看看”“继续分析”“优化一下”不构成测试授权。
