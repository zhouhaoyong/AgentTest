# AgentTest 测试点设计

你当前处于 AgentTest 的测试点设计阶段。

你的目标是：基于当前 Version 已确认的结构化需求，完成测试分析并生成可执行、可评审的测试点文档。

## 一、前置阅读

开始设计测试点前，按以下顺序读取相关资料：

1. 根目录 `AGENTS.md`。
2. 当前 Version 的 `version.yaml`、`requirement.md`、`test-points/` 和其他与当前需求直接相关的资产。
3. `requirements/requirement.md` 中定义的目录契约，以及当前需求对应的结构化需求文档。
4. 当前 Version 的 `analysis/analysis.md`，如果存在。
5. 当前 System 的 `system.yaml`，以及 System 级的：
   - `memory/index.md`
   - `element-map/index.md`

对于 Memory 和 Element Map，只读取与当前需求涉及模块直接相关的内容，避免加载无关上下文。

## 二、测试分析原则

不要直接把需求原文逐条改写成测试点。

应先以软件测试工程师视角完成以下分析：

1. 识别需求涉及的功能模块。
2. 识别核心业务对象、状态和数据变化。
3. 梳理主业务流程及关键前置条件。
4. 识别分支流程、异常流程和失败路径。
5. 识别输入、输出、校验规则和边界条件。
6. 识别角色、权限、数据范围和数据隔离要求。
7. 识别跨页面、跨模块、上下游系统之间的衔接。
8. 识别需求描述中的歧义、缺失条件和潜在风险。

完成分析后，再据此设计测试点。

## 三、测试点文件

生成或更新当前 Version 的：

`projects/<project-name>/systems/<system-name>/versions/<version-name>/test-points/test-points.md`

必须遵守以下约束：

- `test-points/` 必须位于当前 Version 目录下。
- 禁止在项目根目录直接创建 `test-points/`。
- 如果文件已经存在，应基于当前确认需求进行更新，不要无条件覆盖仍然有效的内容。
- 不得修改与本次测试点设计无关的文件。

## 四、测试点设计要求

### 1. 基本字段

每个测试点至少包含：

- 稳定 ID，例如 `TP-001`
- 测试点名称
- 关联需求
- 优先级
- 测试维度
- 测试步骤
- 预期结果

如果确实需要，增加前置条件和测试数据；不需要时不要保留空字段。关联需求应引用明确的需求名称或标题路径，确保能够从测试点反向追溯到需求。

测试点是一个清晰的验证目标，不是完整测试用例。步骤保持简洁但必须可以实际执行，预期结果必须明确、客观、可判断。

### 2. 测试点粒度

一个测试点只表达一个清晰的验证目标。

避免：

- 一个测试点同时验证多个无关行为。
- 使用“检查功能是否正常”之类无法执行的描述。
- 单纯复述需求。
- 把大量不同输入情况全部塞进一个测试点。

## 五、测试维度

根据实际需求选择需要覆盖的维度，不要求为了完整形式强行生成无意义测试点。

### 功能测试

重点考虑：

- 正常操作
- 输入校验
- 必填 / 非必填
- 边界值
- 非法输入
- 数据格式
- 重复操作
- 错误提示
- 状态变化
- 数据新增 / 修改 / 删除
- 数据持久化
- 页面刷新或重新进入后的状态
- 依赖数据不存在或异常时的处理

### 业务流程测试

重点考虑：

- 前置条件
- 主流程
- 分支流程
- 失败路径
- 中断与恢复
- 重复提交
- 跨页面衔接
- 跨模块衔接
- 上下游状态同步
- 流程完成后的最终状态
- 业务数据是否正确保存、流转或展示

不要只验证单个页面操作，应关注完整业务闭环。

### 角色与权限测试

需求涉及角色、权限或数据范围时，必须覆盖：

- 页面 / 功能可见性
- 操作权限
- 不同角色行为差异
- 数据查询范围
- 数据修改范围
- 数据隔离
- 越权访问
- 直接访问受限页面或接口
- 权限变化后的行为

如果需求没有定义权限规则，不得自行推断，应将其记录为开放问题或未覆盖项。

## 六、Element Map 使用约束

Element Map 仅用于帮助定位已经存在的页面、控件和元素。

不得因为 Element Map 中存在某个页面、按钮、输入框、菜单、权限入口或其他元素，就推断需求已经要求该功能或权限成立。

需求是测试范围的主要依据，Element Map 不能代替需求定义。如果 Element Map 与需求不一致，应记录差异，不得自行选择其中一个作为事实。

## 七、需求不明确时的处理

遇到以下情况时不要自行补充业务规则：

- 条件缺失
- 状态定义不完整
- 权限范围不明确
- 输入边界未定义
- 不同文档描述冲突
- 流程结果不明确
- 异常场景没有定义预期行为

将这些问题记录到“开放问题”或“待确认项”，并说明它会影响哪些测试点或测试范围。

如果未确认的问题会改变核心测试范围、业务规则或预期结果，必须先向用户提问，暂停生成受影响的正式测试点。对于不影响当前范围的问题，可以先生成不受影响的测试点，并在“开放问题”和“未覆盖 / 阻塞项”中说明影响。

## 八、测试范围与风险

在 `test-points.md` 中增加测试范围分析，至少记录：

### 已覆盖

说明本次测试点已经覆盖的功能、业务流程、角色 / 权限和重要异常场景。

### 未覆盖 / 阻塞

明确记录以下内容（如果存在）：

- 暂未覆盖的功能
- 无法确认的流程
- 缺少权限定义的场景
- 缺少测试数据或环境依赖的场景
- 被需求歧义阻塞的内容

每项说明原因。

### 开放问题

记录仍需用户确认的问题，并说明对测试点或测试范围的影响。

### 风险

记录可能影响后续测试质量的重要风险，例如：

- 需求描述不完整
- 权限规则缺失
- 跨系统依赖不明确
- Element Map 与实际实现可能不同
- 缺少可验证的预期结果

## 九、建议文档结构

`test-points/test-points.md` 建议按照以下结构组织：

```markdown

状态：Draft

## 1. 测试范围

### 已覆盖

### 未覆盖 / 阻塞

### 开放问题

### TP-001 测试点名称

- 关联需求：

- 测试维度：

- 测试步骤：
  1.
  2.

- 预期结果：
  1.

## 4. 角色与权限测试
```

没有实际内容的测试分类、字段或章节可以省略，不要为了保持模板完整而生成无意义内容。

## 十、优先级原则

测试点优先级使用：

- **P0**：核心业务主流程、关键数据正确性、严重权限或安全问题、失败会导致核心功能不可用。
- **P1**：重要功能、重要分支流程、常见异常和边界场景。
- **P2**：低频场景、体验类问题、影响较小的异常或边界情况。

不要让所有测试点默认使用同一个优先级。

## 十一、强制暂停

完成当前 Version 的 `test-points/test-points.md` 之后，必须立即停止。

此阶段禁止：

- 启动浏览器
- 打开被测系统执行操作
- 调用正式测试流程
- 执行测试用例
- 修改业务数据
- 根据测试点自行开始测试

只有当用户明确表达以下含义之一时，才能进入测试阶段：

- “测试点确认”
- “可以开始测试”
- “按照这些测试点执行”
- 或其他明确授权开始测试的表述

没有得到明确授权时，始终停留在测试点设计阶段。

## 十二、完成后向用户汇报

生成或更新测试点后，只需要向用户汇报：

1. `test-points.md` 相对于项目根目录的路径。
2. 测试点总数。
3. P0 / P1 / P2 数量分布。
4. 已覆盖的功能、业务流程和角色 / 权限维度。
5. 未覆盖或被阻塞的内容及原因。
6. 存在的开放问题。
7. 明确说明：测试点已生成，当前暂停在测试点确认阶段，等待用户确认后再开始测试。
