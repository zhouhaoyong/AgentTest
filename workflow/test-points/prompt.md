# 测试点设计 Prompt

你正在基于当前 Version 或联动范围的最终需求设计可执行、可评审的测试点。测试点描述验证目标，不是完整测试用例。

## 进入条件

- 当前 Version 或联动范围的结构化需求已完成。
- 已完成探索决策；需要探索的部分已完成，或已确认复用已有知识。
- 用户尚未授权开始正式测试。

## 必读资料

1. 根目录 `AGENTS.md` 与当前 Version 或联动范围的配置、`requirement.md`、`requirements/`。
2. 当前范围已有的 `test-points/`（如存在）。
3. 相关 System 的 `system.yaml`、Memory 与 Element Map 模块。
4. [`template-test-points.md`](template-test-points.md)，它是测试点文档的唯一完整模板。

## 决策与执行

1. 先分析功能模块、业务对象和状态、主流程与分支、输入校验与边界、角色权限、页面衔接以及未知项。多个 System 时写清涉及的系统、操作顺序和最终结果在哪里核对。
2. 每个 Test Point 使用稳定 ID、名称、关联需求、优先级、测试维度、必要的前置条件/测试数据、步骤和可判断的预期结果。
3. 按实际需求覆盖功能、业务流程、角色/权限场景；不强行生成无意义分类或字段。P0 表示核心流程、关键数据或严重权限风险，P1 为重要功能和常见异常，P2 为低频或影响较小场景。
4. 统计、指标或汇总需求写清口径、时间范围、筛选条件和参考数据；多个 System 或数据更新有等待过程时，写清等待什么结果和最长等待时间。
5. 在测试范围中记录探索策略（复用已有知识、目标探索或必须探索）、依据、已覆盖、未覆盖/阻塞、开放问题和风险。
6. 需求、Memory 与 Element Map 冲突，或关键未知项会影响测试范围或预期结果时，先向用户提问；不把推断写成测试点。

## 允许写入的位置

- 只更新当前 Version 或联动范围的 `test-points/test-points.md`，使用相邻唯一模板作为结构参考。
- 不修改无关资产，不在 `workflow/` 写真实测试点，不启动浏览器、不修改业务数据。

## 交付物与移交方向

- 向用户汇报测试点路径、数量与 P0/P1/P2 分布、覆盖范围、未覆盖/阻塞项、开放问题和风险。
- 用户明确表示可以开始测试后，移交 `testing/`；执行前由测试阶段重新读取当前文件的完整内容。

## 强制停止条件

- 写完或更新 `test-points/test-points.md` 后立即停止。
- 不写 `Draft`、`Approved` 等批准状态，不执行测试，不调用正式测试流程；“看看”“继续分析”“优化一下”不构成测试授权。
