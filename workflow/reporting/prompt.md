# 测试报告 Prompt

你正在基于已存在的测试证据整理当前 Version 或联动范围的测试报告。

## 进入条件

- 用户只要求整理或更新报告，且本次测试记录、测试用例和 Bug 信息已存在。

## 必读资料

1. 根目录 `AGENTS.md`、当前 Version 或联动范围的配置、`report/requirement.md` 与相关 System 的配置。
2. 当前最终 `test-cases/test-cases.md`、本次实际使用的脚本、测试记录和 Bug 信息。
3. [`template-report.md`](template-report.md) 及必要的 System 索引和环境配置。

## 决策与执行

1. 明确本次执行类型为正式测试或回归测试，只记录实际观察和已有证据。
2. 每个 Test Case 只能记录 `PASS`、`FAIL`、`BLOCKED` 或 `NOT RUN`，并同时记录 `执行覆盖`（完整 / 部分 / 未执行）；只有完整覆盖才能记录 PASS 或 FAIL，并保证总数等于四类结果之和。
3. 回归测试单独统计当前这次执行；历史结果仅作对比。Bug 必须关联测试用例，并使用规定状态和完整复现信息。
4. 明确未测试/阻塞的功能、流程、角色权限场景、风险和建议。
5. 核对需求文档中出现的页面名称、列表名称、按钮名称等界面文案是否与真实页面一致；发现不一致且确有必要时，提示更新结构化需求文档使其与真实界面对齐（并入"测试后实现说明"，引用系统原文保持原文不翻译）。
6. 口径要准确：若本轮没有任何测试用例被有效执行（全部因环境 / 读取阻塞记为 `BLOCKED`），概况与结论表述为"本轮未能执行，因环境 / 读取阻塞"，不写"正式测试已执行"。
7. 交付前做报告自检（逐条核对，不通过就先改再交付）：
   - **汇总自洽**：本次测试用例总数 = PASS + FAIL + BLOCKED + NOT RUN，且等于本次执行的测试用例数量。
   - **Bug 可追溯**：每个 Bug 都关联到具体测试用例，证据引用的 `evidence/` 路径存在且可访问。
   - **无凭据泄露**：报告正文、截图、Trace、HAR 等不含账号、密码、Token、Cookie、Storage State、验证码等敏感信息。
   - **名称一致**：报告与需求文档中的页面 / 列表 / 按钮名称已与真实界面核对一致（或已记录需更新项）。

## 允许写入的位置

- 更新当前 Version 或联动范围的 `report/report.md`；必要时只补齐测试用例中的执行字段（`测试状态`、`测试结果`、`实际说明`、`执行时间`、`证据`），不得改变测试范围。
- 不补测、不修改测试用例的范围内容、需求目标、脚本或业务数据，不保存敏感信息。

## 交付物与移交方向

- 向用户说明执行类型、结果分布、Bug 严重程度分布、未测/阻塞内容、风险、建议和报告路径。
- 报告完成后结束；后续 Bug 修复由用户明确发起回归。

## 强制停止条件

- 记录不足以判断结果时，只能标记缺失或阻塞，不得补测或把推测写成结论。
- 不启动浏览器。
