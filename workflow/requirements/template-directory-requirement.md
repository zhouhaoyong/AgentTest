# requirements 目录契约

## 目录职责

保存本 Version 的原始需求来源和最终结构化需求文档。

## 允许内容

- `source.md`：原始文本、链接和附件引用。
- `attachments/`：用户提供的原始文件及其目录契约。
- `requirement.md`：本目录契约。
- `YYYYMMDD_V<版本号>_<system-id>.md`：最终结构化需求文档。

## 文件职责

保留原始来源，不用 Agent 摘要替换 `source.md`；结构化需求文档使用自然语言、清晰的标题层级和符合业务语义的章节，不强制使用人工需求编号。测试用例通过需求名称或标题路径关联，并在同一文件中按需记录测试后的实现说明。

## 命名规则

结构化需求文档使用：

```text
YYYYMMDD_V<版本号>_<system-id>.md
```

其中：

- `YYYYMMDD` 是文档首次生成日期。
- `<版本号>` 来自用户输入，不强制使用某一种版本号格式；文件名中的版本号需要经过安全规范化。
- `<system-id>` 使用已确认的 System ID（与目录名一致即可，不要求带系统类型后缀）。

同一版本后续补充需求、修复 Bug 或回归测试时，继续更新同一份文档，不重新命名。

## 更新规则

保留原始需求来源；不得把未确认的 Project、System、Version、多端联动关系、角色、权限或行为写成确定事实。测试后的实现说明必须关联当前范围或测试证据，不能静默改写业务需求。

## 禁止事项

- 不要求 AgentTest 为每种附件格式实现 Parser。
- 不用 Agent 摘要替换原始来源。
- 不保存密码、Token、Cookie、Storage State 或其他凭据。
- 不因为页面现状或 Element Map 证据，未经用户确认修改业务目标或需求范围。

## 阅读策略

生成测试用例或执行测试前，先读本契约、`source.md` 和当前范围的结构化需求文档；结构化需求文档通过上述命名规则识别，不把本文件当成业务需求。
