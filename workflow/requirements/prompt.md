# 需求整理 Prompt

你正在审查、澄清并整理当前 Version 或联动范围的需求。最终文档应是简洁、自然的 PRD，而不是测试用例。

## 进入条件

- 当前 Project、相关 System、Version 或联动范围、测试地址和原始需求来源已确认。
- 用户要求整理、澄清或更新需求。

## 必读资料

1. 根目录 `AGENTS.md`、相关 `requirement.md` 与 `prd.md`。
2. 当前 Version 或联动范围的 `requirements/requirement.md`、`source.md` 和已有结构化需求文档。
3. 相关 System 的 `memory/index.md` 与 `element-map/index.md`；仅加载与需求直接相关的模块。

## 决策与执行

1. 原样保留需求来源，审查角色、权限、流程、输入、边界、异常、依赖、范围和风险。多个 System 时，写清各自负责的步骤和顺序。
2. 区分已确认事实、合理推断、待确认问题和明确排除项；关键问题未确认时提问并暂停。
3. 将确认内容整理到当前范围唯一的 `requirements/YYYYMMDD_V<版本号>_<system-or-scope-id>.md`；已有对应文档时更新它，不因日期创建第二份。
4. 涉及统计、指标或汇总时，明确计算口径、时间范围、筛选条件和可参考的数据来源；无法确认时先提问。
5. 完成后执行**探索决策**：
   - **复用已有知识**：相关模块、流程与定位已被 Memory / Element Map 覆盖，信息仍适用当前需求，且没有影响测试设计的关键未知项；直接移交 `test-points/`。
   - **目标探索**：仅缺少本次需求涉及的部分模块、流程或定位；移交 `exploration/`，只探索缺失部分。
   - **必须探索**：没有相关可复用知识、既有知识与需求冲突，或页面流程、权限、状态或依赖无法确定；移交 `exploration/` 完成必要探索。

## 允许写入的位置

- 只写入当前 Version 或联动范围的 `requirements/` 及用户明确要求保留的附件。
- 不在结构化需求中写测试步骤、预期结果、测试状态或 Bug；不执行浏览器测试。

## 交付物与移交方向

- 向用户说明结构化需求路径、遗漏与开放问题。
- 复用已有知识时移交 `test-points/`；需要探索时移交 `exploration/`。测试点将在其“测试范围”中记录最终探索决策及依据。

## 强制停止条件

- 关键业务规则、预期结果或范围不清时，先提问并暂停。
- 不得因为页面现状、Memory 或 Element Map 擅自改变业务目标；不得进入正式测试。
