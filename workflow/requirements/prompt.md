# 需求整理 Prompt

你正在执行 AgentTest 的需求审查、澄清和整理阶段。

最终文档应像一份简洁、自然的 PRD，而不是测试用例、测试点或字段表单。

## 前置阅读

先阅读：

1. 根目录 `AGENTS.md`。
2. 当前目录和目标资产最近的 `requirement.md`。
3. `prd.md` 中与当前任务相关的部分。
4. 当前 Version 的 `requirements/requirement.md` 目录契约、`requirements/source.md` 和已有结构化需求文档（如果存在）。
5. 相关 System 的 `memory/index.md`；仅按需读取相关 Memory 模块。

不要重复询问文件中已经明确的信息。不要把猜测写成已确认事实。

## 输入

使用用户确认的 Project、System、系统类型、Version、测试地址和原始需求来源。

## 执行要求

1. 保留原始需求，不用 Agent 摘要替换 `requirements/source.md`。
2. 先审查原始需求是否完整、清楚、前后一致，再整理结构化需求；至少检查：
   - 角色、权限和数据范围。
   - 前置条件、主流程、分支流程和后置结果。
   - 输入校验、边界值、异常、空状态、状态变化和持久化。
   - 页面、模块、接口、外部系统和数据依赖。
   - 测试环境、测试数据、登录方式和预期业务结果。
   - 本次范围、明确不在范围内的内容、风险和未知项。
3. 对每个遗漏项、矛盾项或无法确认的问题，记录问题、影响、建议方案和待用户确认的选项。
4. 区分已确认事实、合理推断、待确认问题和明确排除项。关键问题没有得到用户回答时，先提问并暂停，不把推断写成确定事实。
5. 将已确认内容整理为一份简洁的产品 PRD，保存为 `requirements/YYYYMMDD_V<版本号>_<system-id>.md`。使用清晰的标题层级组织需求，不强制增加人工需求编号。文件名中的版本号不强制使用 SemVer：保留用户版本号的含义，去除首尾空格，将不适合文件名的字符规范化为 `-`；如果版本号为空或无法判断，先向用户确认。
6. 如果当前 Version 已存在与 System ID 和版本号对应的结构化需求文档，必须复用并更新原文件，不得因为日期变化创建第二份需求文档。
7. 后续 Test Point 通过需求名称或标题路径关联需求；表达不清或无法确认的内容，先向用户提问，或列入待确认事项，不要自行补写成确定事实。
8. 明确区分“业务期望”和“当前页面实现”。页面上的功能按钮不是需求的唯一依据：没有对应按钮不代表需求无效，存在按钮也不代表它属于本次需求。
9. 需求整理完成后，下一步使用 [`workflow/test-points/prompt.md`](../test-points/prompt.md) 生成测试点；测试点生成后按测试点确认规则等待用户批准。
10. 不生成正式测试结果，不执行浏览器测试，不创建 Bug 结论。
11. 不静默覆盖已有内容；修改已有需求时保留原有有效内容，并维持标题层级和章节语义的连续性。

## 需求文档写法

- 使用自然语言描述用户目标、业务诉求和已经确认的业务规则。
- 可以使用段落、列表或表格；多个功能或业务主题使用自然、明确的标题区分，不要把需求拆成测试点式条目。
- 只保留实际有内容的章节，不要生成一组空标题。
- 不在需求文档中写测试步骤、预期结果、测试数据、测试状态或 Bug 结论；这些内容属于测试点和测试报告。需求文档应像正常的产品 PRD，而不是测试用例或字段清单。
- `source.md` 保存原始需求，结构化需求文档保存确认、补全后的需求，不重复粘贴整段原文。

## 需求文档的后续更新

正式测试结束后，如果 Element Map、页面探索或测试结果发现需求与实际实现存在差异，继续更新同一份结构化需求文档，在“测试后的实现说明”中自然补充：

- 观察到的页面行为、元素和定位证据。
- 对应的 Version、Test Point 或报告位置。
- 与原始需求或已确认需求内容的差异。
- 对需求的影响和建议的后续处理。

这些内容是实现事实或澄清记录，不得覆盖 `source.md`，不得未经用户确认修改业务目标或需求范围，也不得因为测试后的补充而重新命名文档。

## 完成后向用户说明

完成后向用户说明：

- 已确认的上下文。
- 需求文档已生成或更新。
- 需求文档相对于项目根目录的路径，例如 `projects/gumai/systems/gumai-web/versions/v1/requirements/20260814_V2026.08.04_gumai-web.md`。
- 审查出的遗漏、矛盾、边界和建议方案。
- 需求中仍然存在的开放问题。
- 建议下一步使用 [`workflow/test-points/prompt.md`](../test-points/prompt.md) 生成测试点。

如果关键上下文仍缺失，先提问，不创建正式业务资产。
